## 审核结论

**判定：设计文档整体合理、基本遵循需求文档，可作为实施基线；但存在 6 项阻塞缺口需在编码前补齐，另有 9 项应修正项与 14 项一致性问题。**

需求追溯质量高于常见水平：48 条需求中约 42 条具备「REST 端点 + 表结构 + 领域函数 + 正确性属性」四重落位。三处最易出错的架构判断均正确：

1. **WBS 与工卡类型合并**为 `card_type` 单列（需求 6.8），IR 卡判定以 `card_type='04'` 为准，未建冗余 `wbs` 列。
2. **条码归执行域** `job_process` 且编制态不生成（需求 15.3），规避了同一工卡多次维修复用同一条码的缺陷。
3. **执行期字段落 `job` 而非 `task_card`**，正面回应需求 26.2「编制态不呈现空壳栏位」与需求 37.5「两域分离」。
4. **`UNIQUE(task_no) WHERE status='Effective'` 部分索引**把需求 38.7/44.7 的单一生效版本做成数据库级不变式，而非仅应用层校验——适航场景下强度正确。
5. **五态 `ALLOWED_TRANSITIONS`** 与需求 4.5 逐条比对完全一致，终态无出边符合需求 4.7。

## 一、阻塞项（编码前须补齐，共 6 项）

### B1. 工卡关联无数据模型，连带使 Property 27 失去数据锚点

- **现象**：§1.2 定义了 `POST/DELETE/GET /api/task-cards/:id/relations`，组件表亦列有 `CardRelationPanel`，但 Data Models 全篇无 `card_relation` 表。
- **连带影响**：需求 45.8/45.9 与需求 16.4 的联动（「签署要求属性为『签署』的单据若未配置签署项则阻止提交」）要求工卡能定位到其所涉**执行过程单据类型**，而 `task_card` 无 `exec_doc_type` 列、关联表亦不存在，Property 27 后半句不可实现。
- **另缺**：需求 21.4（执行期产生 PC/CR/TS 单据时**自动**建立关联）与 21.5（关键信息变更同步至关联记录）在设计中无任何服务、领域函数或触发点。
- **涉及需求**：21.1–21.5、45.8、45.9、16.4
- **性质**：需求有 SHALL、设计无落位对象

### B2. 身份认证与用户主数据缺失，需求 47 权限体系悬空

- **现象**：设计有 `middleware/authorize.js`、`role_permission` 表、`GET /api/me/permissions`，但无 user/session 表、无登录端点、无 token 方案——「当前用户与其角色从何而来」未定义。
- **连带影响**：
  - 需求 22.3 一编一审依赖 `created_by` 与当前用户比较；
  - 需求 7.4 `operator_id` 自动记录无来源；
  - 需求 1.3「当前用户有权访问的全部工卡」的**行级数据权限**在设计中无任何体现，且 Property 4 反而断言「所有条件为空时结果等于全集」，与 1.3 语义相左，二者需择一定案；
  - 需求 47.10「记录越权尝试」无审计表承载（`change_record` 语义不符）。
- **涉及需求**：47.1–47.10、22.3、7.4、1.3
- **建议方向**：即便当前为演示阶段，亦需至少落一张 `app_user(id, staff_no, name, role)` 与请求侧用户标识传递方案，否则一编一审与权限属性测试无法闭环。

### B3. 需求 46.12 与 46.5/46.6 逻辑互斥，设计未给出路

- **现象**：`autoFillStage(cardType, cfg)` 与 `MetadataForm`「选定类型后自动填入并只读」按字面实现了需求 46.12。但工卡类型 01–10 的 Stage 一旦只读，用户**永远无法将其标记为 WFD**，而需求 46.5 要求 WFD 工卡排除于 Load Standard Package、46.6 要求清单显著标识并可按 WFD 筛选批量处置。
- **矛盾定位**：Property 28 同时断言了「单一允许 Stage 的类型自动填入」与「WFD 恒排除于取卡结果」两侧，逻辑上不可同时满足。
- **根因**：源自需求侧（临时设计说明 A4-2/A4-3 的 Hotfix 假定），但设计层需给出可实施出路。
- **涉及需求**：46.5、46.6、46.12、46.13

### B4. 商务分类 P1–P5 五个判定源全部无数据来源

- **现象**：`deriveCommercialClassification(card, sources, priorityCfg)` 函数签名设计良好，但 `sources` 的来源未定义——计划端 Dummy Job 标记、实际 NRC 发起单据、实际外包清单、零件寿命件性质、工包划分分类五者，在 Data Models 与 §1.9 集成端点（仅 TPC / PPC / PID scope）中均不存在。
- **后果**：仅 P6 类型兜底可运行，P1–P5 无法运行；而 Property 23 断言的正是「结果等于优先级链中**首个命中层级**给出的分类」，该属性无法验证。
- **已具备**：`derivation_priority_config`（顺序可配，需求 29.8）与 `commercial_classification_result`（追加式审计轨迹，需求 29.5/29.6）两张表设计正确，缺的是输入侧。
- **涉及需求**：29.1–29.5、43.3、43.4

### B5. 需求 42.1(c)「在编（尚未释放）工包已选入」无数据来源

- **现象**：`work_package_release` 仅记录已发布结果，设计无承载「在编工包已选入某工卡」的表或集成端点。
- **后果**：`checkVoidPrecondition(card, refs, reason)` 的 `refs` 取不到第三类引用，`GET /api/task-cards/:id/void-precheck` 只能返回两类，需求 42.2「提示具体的引用类型与引用位置」无法完整实现。
- **涉及需求**：42.1、42.2

### B6. 附件（图片/视频/音频）存储方案缺失

- **现象**：设计仅在 `inserted_component.payload` 中约定 `{url}`，Error Handling 表已列「图片/视频/音频上传失败 → 400」，但**无上传端点、无存储位置约定、无 attachment 表**。
- **涉及需求**：13.2（维修草图）、13.3、18（图文混编）、31.2（视觉提示支持图片或视频）、5.3（打印含维修草图）
- **性质**：三大界面中工作量与风险均不小的一块留白

## 五、风险提示

`docs/临时设计说明-待澄清项与Hotfix-20260809.md` 将 **A4-4（存量工卡 Stage 与类型强约束的兼容性）** 列为最高复核优先级，其当前处置为「逐条跳过 + 记录原因 + 输出迁移报告」。该策略本身正确，但设计侧的迁移解析层（本报告 S7）恰为最薄弱环节。两者叠加意味着：迁移一旦启动，可能同时面临「Word 解析不出来」与「大量 Stage×类型组合不合法」两类失败，且难以区分根因，业务方返回后亦无法依报告作出有效裁定。

**建议**：迁移（需求 17、41）单独立项评估，不与主编制流程并行推进。

## 六、建议的处理顺序（供参考，本报告不含任何修改动作）

1. 补齐三张缺失表与其端点契约：`card_relation`（含 `exec_doc_type` 挂接）、附件表、最简 `app_user`——三者为 Property 27、需求 13/31、需求 22.3/47 的前置。
2. 定案需求 46.12 与 WFD 标记的冲突，并同步修订 Property 28 与 requirements.md 46.12。
3. 补齐商务分类 P1–P5 判定源与「在编工包引用」的集成端点，使 Property 23、Property 24 可落地。
4. 修补校验闭环三处：submit-review 补 Stage 校验（S1）、`isFrozen` 纳入 UnderReview（S2）、`canRelease` 归位（S3）。
5. 在 Testing Strategy 中拆分「纯函数属性」与「事务/隔离属性」，重挂 Property 11/13/25/31（S9）。
6. 迁移解析层（S7）与打印/导出产物格式（S8）各补一节；C8（localStorage 列配置）、C3（需求 27 编制态处置）登记进《临时设计说明》附录「开发期新增待确认项」。
