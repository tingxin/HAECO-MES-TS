## 业务方休假期间的处置原则

业务方已进入休假，本项目采取以下原则继续推进：

1. **不停工等待**。所有未确定事项均给出可运行的 Hotfix 假定，开发按 Hotfix 推进。
2. **一律登记**。任何新出现的不确定点、实现过程中的推断决策，均追加至本文档「附录：开发期新增待确认项」一节，不散落在代码注释或聊天记录中。
3. **配置驱动**。Hotfix 一律实现为配置表 + 默认数据，业务方回来后改配置即可，避免返工改代码。
4. **就地标注**。requirements.md / design.md 中所有 Hotfix 假定处均带〔Hotfix 假定，见《临时设计说明》X〕或 `⚠ Hotfix 假定` 标记，便于批量定位。
5. **复核清单**。业务方返回后，以本文档「汇总」与「附录」两节作为逐项复核清单。

## 使用约定

1. 所有 Hotfix 假定在 requirements.md 与 design.md 中以〔Hotfix 假定，见《临时设计说明》X〕或 `⚠ Hotfix 假定` 就地标注，便于澄清后定位替换。

## A1. 商务分类候选聚合与确认口径（2026-08-10 已裁定）

### 业务方裁定（2026-08-10）

1. **优先顺序定案**：P1 计划设置 → P2 实际发起单据 → P3 实际外包清单 → P4 零件性质 → P5 工包划分 → P6 工卡类型映射。
2. **派生口径定案**：评估全部启用层级并聚合全部不同分类候选；相同分类合并全部 sources，首次命中的层级决定候选排序。非类型 11 的首候选为推荐；单候选自动 `derived`，多候选持久化 `requires_confirmation`。
3. **类型 11 定案**：不评估 P1–P5，固定返回 Material Special Replacement 与 Configuration(MOD) 两个候选，`recommendedClassification=null`，必须由 TS 确认其一。该项不再待澄清。
4. **证据与确认定案**：每个候选保留首次 `hitTier/sourceRef` 与全部 `{hitTier,sourceRef,outsourceSubtype}` sources；确认须携带最新 `derivationResultId` 和完整候选，Outsource 必须携带 subtype。
5. **权威值定案**：`task_card.commercial_classification/outsource_subtype` 是当前权威值；pending/undetermined 只追加审计轨迹，不清空既有权威值，derived/confirmed 才同步更新。

**落地位置**：需求 29、34.1(h)、43；分类 derive/latest/history/confirm API；`commercial_classification_result`；Property 23；前端 `TaskCardEditorView`、`ReviewPanel`、`ClassificationConfirmDialog`。

### 仅保留的未回答项

- 是否存在**蓝图未列出的其它外部判定源**。当前不预设额外来源；业务方若补充，应另行确认数据所有者、读取契约、候选证据格式及在既定 P1→P6 中的插入位置。

### 裁定后影响面

本项已完成规范与前端回填。优先级配置仍可用于启停及证据排序，但不得改变类型 11 已裁定特例；新增蓝图外来源属正式变更，不再作为当前 Hotfix 待确认项。

## A3. 编制域签署项定义（P1）

### 待澄清问题

I.8 要求「Column for Staff Signature, stamp and Date of Completion」；需求 32.4 引用「工卡全部必需签署项」，但组件清单无签署组件，且无 AC 定义：谁在编制阶段决定哪些工序需签署、由什么角色签署、是否需盖章。**必需签署项无来源，32.4 无法验证。**

### 已实施 Hotfix

- 组件清单增加 `signature`（签署栏）类型（需求 13.1）。
- 新增**需求 45 工序级签署要求配置**：工序可配置是否需签署、签署角色（可多个）、是否盖章、完成日期。
- 明确「工卡下全部工序签署项集合」为需求 32.4 必需签署项的**唯一来源**（45.6）。
- 与需求 16.4 联动：签署要求属性为「签署」的单据若未配置签署项，提交审核时阻止（45.8、45.9）。

**签署角色集合（Hotfix 假定）**：`{执行人 Operator, QC 检验 QC, NDT 检验 NDT, 授权放行人 Certifying Staff}`

**落地位置**：需求 13.1、45.1–45.9；`SIGNATURE_ROLE`、`signature_requirement` 表；Property 27。

### 待业务方澄清

1. **签署角色集合是否完整、命名是否准确**——是否需增加如「工段长」「适航审核」等角色。
2. **盖章要求**：哪些角色/工序类型强制盖章，是否与授权放行人绑定。
3. 是否存在**签署顺序**要求（如必须 Operator 先签、QC 后签）。当前 Hotfix 仅按 `sort_order` 排序展示，未强制签署时序。
4. 一个工序是否允许同一角色配置多个签署项。

### 澄清后影响面

**中**。角色集合存于 `SIGNATURE_ROLE` 枚举与 `signature_requirement.signature_role` 的 CHECK 约束，增删角色需一次轻量迁移。若确认需要**签署时序强制**，则需新增前置校验逻辑与一条属性，属新增功能而非改造。

## A4. Stage 与工卡类型、工卡状态的维度关系（P1）

### 待澄清问题

Stage 取值中 **WFD（wait for delete）与工卡状态「作废」语义重叠**，关系未定；NRC/MOD/CUS 与工卡类型 10/11、商务分类的对应也未定。此问题直接影响蓝图 2.3.6 的 Load Standard Package（依 TPC + A/C Type + Gear Type + Stage=RTN 取生效工卡组包）取数口径。

### 业务方裁定（2026-08-09）

> **「Stage 与工卡类型是否存在强约束 —— 存在强约束。」**

据此推翻了本项原先「三维完全独立」的 Hotfix，改为：**Stage 与工卡类型存在强约束**，工卡状态仍与二者独立。

### 已实施 Hotfix（修订版）

新增**需求 46**，维度关系如下：

| 维度 | 含义 | 与其它维度关系 |
|------|------|--------------|
| Stage | 工卡用途/阶段归属 | **与工卡类型强约束**（见下表） |
| 工卡类型 01–11 | 工卡业务种类 | **与 Stage 强约束** |
| 工卡状态 | 生命周期 | 与前两者**独立**，不由其派生 |

**Stage × 工卡类型约束表**（⚠ 具体映射为 Hotfix 假定，依蓝图「工卡类型区分」表说明列推导）：

| 工卡类型 | 蓝图说明列 | 允许 Stage | 自动填入 |
|---------|-----------|-----------|---------|
| 01–09 | Routine（01 另含 Gear Inspection） | `RTN` | 是（选定类型后自动填入并只读） |
| 10 AD/SB/SL 卡 | SB、AD、SL | `SPC`（Special Work Card） | 是 |
| 11 客户特殊要求卡 | 例如 EO/ER、Configuration (MOD) | `CUS`、`MOD` | 否（二选一，人工选择） |

**横切 Stage 取值**（⚠ Hotfix 假定）：`{DMY, NRC, WCC, WFD}` 不受工卡类型约束，可与任意类型共存，不触发校验阻止。理由：DMY 由计划设置、NRC 对应执行期衍生单据（NR）、WCC 为保修索赔场景、WFD 为待删除标记，四者均为跨类型的横切标记而非类型专属阶段。

**校验时机**：保存与提交审核时校验组合合法性，不合法则阻止并提示该类型允许的 Stage 范围（46.10、46.11）。

**落地位置**：需求 46.1、46.9–46.14；`stage_card_type_constraint`、`stage_crosscut` 表；Property 28 改写。

**WFD 处理（Hotfix 假定）**：
- WFD 定义为「已标记待删除但尚未执行作废」，**不等同于**状态「作废」（46.4）。
- WFD 工卡从 Load Standard Package 取卡结果中**排除**，即使状态仍为生效（46.5）——这是保证组包口径正确的关键。
- 清单显著标识 + 支持按 Stage=WFD 筛选以便批量处置（46.6）。
- **不**由 WFD 自动触发作废；作废仍须走需求 42 流程与前置校验（46.7）。
- Stage 不派生商务分类（46.8）。

**落地位置**：需求 46.1–46.8；Property 28。

### 剩余待业务方澄清（休假期间按 Hotfix 推进）

| 序 | 待确认 | 当前 Hotfix 假定 | 影响面 |
|----|-------|----------------|-------|

## A6. IR Lot 卡与 Lot List 的 Base Number 关联（P1）

### 待澄清问题

蓝图 2.3.6 BOM List 字段明确要求「Lot Number：Task Card 所关联的 Lot list 带出 Base，也显示在清单中」。原需求 8 仅给出 IR 卡（04）的 Base Number 与 IPC 项号，**未定义 05 IR Lot 卡如何关联 Lot list 并向 BOM List 输出 Base**。此链路断裂将导致单脚 BOM、零件跟踪与构型管理缺数据。

### 已实施 Hotfix

新增**需求 48**：

- 类型 05 可关联一个或多个 Lot List（对应执行单据类型 LT），记录 Lot Number（48.1、48.2）。
- 从所关联 Lot List 带出其 Base Number 集合（48.3）。
- BOM List 输出为**两来源并集**：04 直接维护的 Base + 05 经 Lot List 带出的 Base（48.4）。
- 输出携带 Task Card No、Task Title、Base Number、Lot Number（48.5）。
- Lot List 来源的 Base 标识其 Lot Number 以区别于直接维护（48.6）。
- Lot List 的 Base 集合变更时同步更新输出（48.8）。

**落地位置**：需求 48.1–48.8；`lot_list_link`、`bom_base_output` 表；Property 30。

### 待业务方澄清

1. **Lot List 的数据归属**——Lot List（LT 单据）由本模块编制，还是属独立模块（LGS-TS-03-04 LOT CHECK/RECORD LIST）？当前 Hotfix 假定为**独立模块**，本模块仅建立关联并读取其 Base 集合。
2. **上级件名称与 LRU 标记的维护界面归属**——蓝图将其列在 Work Package List 的 BOM List 界面。当前 Hotfix 假定归属 **Work Package List 模块**，本模块仅保证 Base Number 输出完整（48.7 已标注）。
3. 同一 Base Number 由 04 与 05 两来源重复输出时的**去重规则**——当前 Hotfix 未去重（保留两条并各自标识来源），待确认是否需合并。

### 澄清后影响面

**低到中**。关联与输出逻辑独立于主编制流程。若裁定需去重，仅需在 `bom_base_output` 汇总时加一层归并；若 Lot List 实为本模块编制，则需新增 LT 单据的编制功能（属新增范围，需评估工作量）。
